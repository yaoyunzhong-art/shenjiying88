# 系统边界矩阵

## 1. 目的

本矩阵用于冻结本项目在“54名行业与技术专家联合审计与规划方案 v2”中的审计边界，避免后续出现以下问题：

1. 只按 `TOB / TOC / Admin` 三端统计，遗漏真实交付面
2. 把 `API`、`App`、`Miniapp`、`Mobile`、`Pad`、`OpenAPI Portal` 视为附属对象
3. 在未冻结边界前直接讨论“全端完成率”
4. 将 mock、fallback 或演示入口误算为正式交付边界

本矩阵是正式启动多轮专家审计前的前置 gate 之一。

## 2. 冻结原则

1. 系统边界按“真实可部署应用 + 核心服务面 + 专项能力面”三层划分。
2. 每个边界对象必须标明：
   - 审计级别
   - 业务定位
   - 技术形态
   - 当前纳入理由
   - 统计规则
3. 未纳入“必须审计”或“抽样审计”的对象，不得并入全局完成率。
4. 凡是 fallback、mock、演示入口，只能作为“现状风险”记录，不得替代正式交付对象。

## 3. 审计级别定义

### 3.1 必须审计

满足以下任一条件即归入必须审计：

- 属于真实可部署主应用
- 承担核心业务链路或统一服务母机职责
- 直接影响三端或多端的一致性结论

### 3.2 抽样审计

满足以下条件可归入抽样审计：

- 是真实交付面，但当前不作为本轮主统计口径
- 与核心链路有耦合，需要验证代表性链路
- 可通过关键路径抽样判断健康度

### 3.3 专项纳入

不一定是单独应用，但必须以专项方式纳入审计：

- 权限与租户隔离
- 审计底座
- 网关 / Webhook / OpenAPI
- 运行时治理 / 回放 / 可观测性

### 3.4 暂不纳入

满足以下条件可暂不纳入：

- 仅为实验、脚手架或中间层占位
- 没有独立交付责任，也不影响当前全端结论
- 尚未形成稳定可评审对象

## 5. 必须审计边界

### 5.1 `apps/api`

- 定位：M5 唯一总母机，统一承载业务 API、多租户、权限、治理与审计。
- 纳入理由：
  - 所有三端和配套客户端最终都依赖它
  - 权限、租户、审计、网关能力都集中在这里
  - 不审计 API，就无法得出任何“全端链路完成”结论
- 统计规则：
  - 必须纳入全局完成率与高危缺口清单
  - 权限、租户、审计、开放平台四类问题全部从 API 作为根面收口

### 5.2 `apps/admin-web`

- 定位：管理后台，承载工作台、治理、配置、审批、运营、报表、财务等关键后台能力。
- 纳入理由：
  - 是角色工作台审计主战场
  - 已形成 264 页量级的真实页面面
  - 与 API 权限、治理、审计专项高度耦合
- 统计规则：
  - 计入全局完成率
  - `Pad` 相关视图以抽样附录方式补充

### 5.3 `apps/storefront-web`

- 定位：TOC 官网 / 门店消费者门户。
- 纳入理由：
  - 承担会员、下单、预约、支付、内容与转化链路
  - 是用户侧业务闭环的主交付面
- 统计规则：
  - 计入全局完成率
  - 交易、预约、支付、会员链路必须单独穿透审计

### 5.4 `apps/tob-web`

- 定位：TOB 官网 / 企业与品牌门户。
- 纳入理由：
  - 承担品牌展示、招商、开放平台、企业协同等业务
  - 是 TOB 审计与官网配置联动的主交付面
- 统计规则：
  - 计入全局完成率
  - `openapi-portal` 作为门户子面抽样加强

## 6. 抽样审计边界

### 6.1 `apps/app`

- 定位：通用移动端 App 入口。
- 纳入理由：
  - 已在现状基线中被统计为核心交付面之一
  - 存在真实业务旅程与动作回放链路
- 审计方式：
  - 抽样关键角色旅程
  - 抽样核心交易或会员链路
- 统计规则：
  - 单列统计，不直接并入主三端完成率

### 6.2 `apps/mobile`

- 定位：离线优先移动端。
- 纳入理由：
  - 是真实应用模块
  - 面向线下和离线场景，不能完全忽略
- 审计方式：
  - 抽样离线场景
  - 抽样会员/订单/门店操作
- 统计规则：
  - 单列统计

### 6.3 `apps/miniapp`

- 定位：微信/支付宝等生态入口。
- 纳入理由：
  - 具备门店运营和管理人员使用场景
  - 与会员、采购、兑换、客服等功能有关
- 审计方式：
  - 抽样登录门禁
  - 抽样会员与业务高频入口
- 统计规则：
  - 单列统计

### 6.4 `admin-web/pad`

- 定位：Pad 版工作台入口。
- 纳入理由：
  - 已在管理后台工作台中显式暴露
  - 属于真实视图面，而非纯概念对象
- 审计方式：
  - 并入 Admin 的附录抽样
- 统计规则：
  - 不单独计端

### 6.5 `tob-web/openapi-portal`

- 定位：开放平台门户子面。
- 纳入理由：
  - 与网关、Webhook、OpenAPI 治理形成外部入口
  - 容易被误判为“已完成门户”，需要单独抽样
- 审计方式：
  - 抽样门户展示、开发者入口、配置联动
- 统计规则：
  - 单列开放平台附录

## 7. 专项纳入边界

### 7.1 权限与租户隔离

- 纳入理由：
  - 角色工作台审计必须依赖正式权限和租户隔离
  - 不属于单一应用，但穿透所有主端
- 结论规则：
  - 不允许只看前端门禁
  - 必须同时看 API metadata、Tenant Scope、RBAC 契约和回归证据

### 7.2 审计底座

- 纳入理由：
  - 是 E54 专项的核心
  - 决定写操作是否可追踪、可回放、可举证
- 结论规则：
  - 必须以专项方案单列
  - 不得被一般功能排期稀释

### 7.3 网关 / Webhook / OpenAPI

- 纳入理由：
  - 面向外部调用与开发者生态
  - 同时涉及权限、安全、限流、治理、审计
- 结论规则：
  - 必须看门户子面 + API 控制面 + 治理链路

### 7.4 运行时治理 / 回放 / 可观测性

- 纳入理由：
  - 直接决定故障恢复、治理回放和风险处置能力
  - 是专家复审中明确要求提升为硬门禁的对象
- 结论规则：
  - 必须按专项能力复核，不按单页完成代替

## 8. 暂不纳入规则

以下对象在未形成稳定交付责任前，暂不计入本轮边界矩阵：

1. 纯脚手架目录
2. 仅为开发调试存在的临时页面
3. 只有演示 UI、没有稳定业务归属的原型页
4. 仅有 mock 数据、无真实 API 归属，且未被产品或交付明确列为首发范围的对象

## 9. 统计与汇报规则

### 9.1 全局完成率

全局完成率只允许覆盖：

- `apps/api`
- `apps/admin-web`
- `apps/storefront-web`
- `apps/tob-web`

### 9.2 附录完成率

附录或抽样完成率单列：

- `apps/app`
- `apps/mobile`
- `apps/miniapp`
- `admin-web/pad`
- `tob-web/openapi-portal`

### 9.3 专项结论

专项对象单独出结论，不并入页面/应用完成率：

- 权限与租户隔离
- 审计底座
- 网关 / Webhook / OpenAPI
- 运行时治理 / 回放 / 可观测性

## 10. 使用要求

后续所有专家审计文档、缺口清单、路线图和复签材料，必须显式引用本矩阵中的边界级别：

- `必须审计`
- `抽样审计`
- `专项纳入`
- `暂不纳入`

未引用本矩阵的“全端完成”“全链闭环”“三端一致”类结论，视为不合格结论。
