## 三、Phase -1: 能力审计 (新增 — 最重要变更)

### 3.1 触发条件
**任何新模块的第一次编码之前，必须先完成能力审计。**

### 3.2 审计清单

```yaml
能力审计检查表:
  后端:
    - [ ] 列出项目所有 NestJS module (ls apps/api/src/modules/)
    - [ ] 识别与当前需求相关的已有模块 (≥3个关键词匹配)
    - [ ] 检查每个相关模块的: controller端点 / service方法 / DTO类型 / 测试覆盖
    - [ ] 判断哪些能力可复用、哪些需扩展、哪些需新建
    - [ ] 输出《能力对齐矩阵》

  前端:
    - [ ] 列出 @m5/ui 已有组件 (grep "export" packages/ui/src/index.tsx)
    - [ ] 列出已有页面路由 (find apps/*/app -name "page.tsx")
    - [ ] 检查是否有功能重叠的页面/组件
    - [ ] 输出《组件复用清单》

  数据库:
    - [ ] 列出 Prisma schema 中所有 model (grep "^model" schema.prisma)
    - [ ] 识别可复用的表/字段
    - [ ] 确定新增表是否与已有表有外键关系
```

### 3.3 Gate 0: 能力审计通过标准

| 检查项 | 通过条件 |
|:---|:---|
| 能力矩阵 | 已列出所有相关已有模块及其能力清单 |
| 复用决策 | 每个能力点标注: 复用/扩展/新建 |
| 重复检测 | 确认无重复造轮子 |
| 数据模型 | 新表与已有表的关联关系已定义 |
| 组件复用 | 前端组件索引已完成 |

**Gate 0 不通过 → 不得进入 Phase 0**

## 四、Phase 0: 事前设计 (强化版)

### 4.1 PRD 模板 (强制字段)

```markdown
# PRD-xxx: [模块名称]

## 能力对齐 (Phase -1 产出)
| 能力 | 已有系统 | 决策 | 理由 |
|:---|:---|:---|:---|
| 支付 | cashier/ | 复用 | 已有微信/支付宝 |
| 推送 | push/ | 复用 | 已有P0-P3多通道 |

## 数据模型
- 新增表: xxx (字段/索引/关联)
- 复用表: xxx (已有字段/需加字段)

## 安全基线
- 认证方案: @Public() / Guard / JWT
- Rate Limit: Y/N (频率)
- CSRF: Y/N
- 数据隔离: tenantId 字段
```

### 4.2 Gate 1: 事前设计通过标准

| 检查项 | 通过条件 |
|:---|:---|
| 能力对齐矩阵 | 所有能力点有已有系统映射 |
| 数据模型 | Prisma schema已设计 |
| 安全声明 | 认证/Rate Limit/CSRF/隔离 四维度已标注 |
| 54预审 | 至少对口3位专家预审通过 |

---

## 五、Phase 1-4: 编码→上线 (保留V1.0主干)

### Gate 2-5 无重大变更，强调以下几点:

1. **Phase 1编码阶段即引入真实DB** — 不再允许"mock以后再改"
2. **安全在编码阶段同步做** — CSRF/Rate Limit随第一个端点一起写
3. **前端组件优先查@m5/ui** — 任何UI元素先查已有组件库

---

## 六、检查单: 新模块启动前 10 问

```
Q1: 这个模块的能力，已有系统有没有？
Q2: 哪些可以复用？哪些必须新建？
Q3: 数据库表设计好了吗？关联表呢？
Q4: 安全四维度: 认证/Rate Limit/CSRF/隔离？
Q5: 前端组件库有现成的吗？
Q6: 54专家团至少3人对口预审了没有？
Q7: mock数据有明确的→真实DB切换时间点吗？
Q8: 跨模块数据闭环验证过了吗？(预约→支付→推送→会员)
Q9: 测试用例覆盖了阻塞项吗？
Q10: 上线前检查单逐项✅了吗？
```
