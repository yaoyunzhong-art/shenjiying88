# 54名行业与技术专家联合审计与规划方案 v2

## 1. 任务目标

面向 `TOB 官网`、`TOC 官网` 与 `管理后台系统`，组织“54名行业与技术专家联合评审”模式，完成以下三阶段工作：

1. 前期筹备：系统性研读 PRD、开发规范宪法、技术说明、阶段路线图、需求卡、模块设计文档，并熟悉现有已开发功能、复用组件和技术架构。
2. 多轮对齐审计：围绕不同角色工作台、权限、流程和三端功能完整性开展多轮审计，识别需求偏差、功能缺口、逻辑冲突与实施风险。
3. 规划输出：形成可落地的里程碑、优先级、资源配置、迭代节奏、质量关口与风险预案，指导后续开发推进。

### 1.1 文档定位

本文件定位为：

- `54名专家联合评审总控方案`
- 用于统一审计组织方式、边界、轮次、门禁、里程碑和治理机制
- 不替代单个专项实施方案

本文件明确要求与以下专项文档配套使用：

- `E54 审计底座专项实施方案`
- `阶段规划、里程碑、资源配置与风险预案`
- `角色主数据字典`
- `系统边界矩阵`
- `三端需求与现状对齐表`
- `缺口清单 + 优先级路线图`

### 1.2 专项边界

为避免“总方案”和“专项方案”混杂，后续执行采用双层文档结构：

1. 本文件负责：
   - 54 名专家的编组与协作方式
   - 审计轮次与里程碑
   - 全局 gate、RACI、质量门禁、风险矩阵
   - TOB、TOC、后台及配套客户端的总审计边界
2. `E54 审计底座专项实施方案` 负责：
   - 审计事件模型
   - `trace_id` 贯通
   - `EventStore`
   - 哈希链、防篡改、不可变快照
   - 留存、归档、查询、回放、取证与恢复演练

### 1.3 前置阻断条件

在正式启动第 2 轮及之后所有专项审计前，必须先冻结以下四份基础工件：

1. `角色主数据字典`
2. `系统边界矩阵`
3. `底座阻断清单`
4. `证据字段标准`

未冻结以上四项，角色工作台、权限和跨端链路审计不得视为正式启动。

## 4. 系统边界与现状基线

### 4.0 系统边界矩阵原则

本次联合审计不再只采用“三端”口径，而是采用“多客户端矩阵”：

- `必须审计`
  - TOB 官网
  - TOC 官网
  - 管理后台
  - API
- `抽样审计`
  - App
  - Pad
  - Miniapp
  - OpenAPI Portal
- `专项纳入`
  - 审计底座
  - 权限与租户隔离
  - 网关 / Webhook / 开放平台

系统边界矩阵冻结前，不得统计“全端完成率”。

### 4.1 TOB 官网

- 基于 Next.js App Router，具备多市场、多租户、多品牌门户结构。
- 已有品牌官网、开放平台、企业入口等模块。
- 重点基线：
  - 门户 bootstrap 已成型
  - 多语言与治理模型已接入
  - 仍需核查各角色面向 B 端客户/运营人员的工作台闭环是否完整

### 4.2 TOC 官网

- 当前主体为 `storefront-web` 门店门户体系。
- 已存在首页、H5、多端门店作用域与门店门户 bootstrap。
- 重点基线：
  - 用户入口和交易/预约/会员功能已具雏形
  - 仍需审计用户旅程、支付闭环、会员闭环与活动转化链条

### 4.3 管理后台

- 已存在大量模块页面与角色工作台入口。
- 后台首页已具备指挥台、治理、告警、审批与工作台入口。
- 重点基线：
  - 页面数量多，功能域覆盖广
  - 不同角色工作台、权限门禁、实际后端能力的一致性仍需系统审计

## 5. 多轮对齐审计框架

### 第 1 轮：资料共识轮

目标：让全部专家统一项目背景、术语、角色、边界与技术底座。

审计项：

- PRD 与 roadmap 是否存在版本冲突
- 开发规范宪法与当前工程执行是否一致
- 三端边界与 API 边界是否清晰
- 已实现模块与 PRD 是否具备映射表
- 角色命名与 RBAC 正式角色名是否存在冲突
- 是否存在 mock / fallback / 假 API 被误记为已完成

输出：

- 《资料共识表》
- 《版本冲突清单》
- 《术语与角色统一表》
- 《角色主数据字典》
- 《系统边界矩阵》
- 《底座阻断清单》
- 《证据字段标准》

### 第 2 轮：角色工作台审计轮

目标：从角色视角核查每个工作台是否“有入口、有权限、有流程、有数据、有闭环”。

启动条件：

- 《角色主数据字典》已冻结
- 《系统边界矩阵》已冻结
- 《底座阻断清单》已过首次复核
- 《证据字段标准》已发布

角色范围：

- 系统管理者
- 平台运营人员
- 租户管理员
- 品牌管理者
- 门店管理者
- 收银/前台
- 导玩/导购
- 仓库/设备/教练等现场角色
- 会员/消费者

审计项：

- 工作台入口完整性
- 导航与任务流顺畅性
- 核心 KPI 与待办是否匹配角色职责
- 页面门禁与后端权限是否一致
- 是否存在 mock 页面、假 API、未联调页面
- 是否存在功能重复、逻辑断裂、角色越权或缺权
- 是否具备真实 API 联通证据
- 是否具备 E2E 链路或等价回归证据

输出：

- 《角色工作台能力矩阵》
- 《角色-权限-流程一致性审计表》
- 《工作台缺口清单》

### 第 3 轮：三端模块对齐轮

目标：审计 TOB 官网、TOC 官网、管理后台三端需求与当前实现的一致性。

审计维度：

- TOB 官网：品牌展示、招商/企业入口、开放平台、内容策略、SEO、多语言
- TOC 官网：门店门户、交易链路、预约、会员、支付、活动、内容、转化
- 管理后台：工作台、治理、配置、审批、报表、财务、运营、AI、开放平台
- 配套客户端：App、Pad、Miniapp 的关键链路抽样一致性

输出：

- 《TOB 功能对齐表》
- 《TOC 功能对齐表》
- 《管理后台对齐表》
- 《配套客户端抽样对齐表》
- 《跨端链路断点清单》

### 第 4 轮：流程与权限轮

目标：按关键业务链路验证权限合理性、流程顺畅性与异常处理完备性。

关键链路：

- 门店开通 -> 官网展示 -> 用户转化
- 会员注册/登录 -> 下单/预约 -> 支付 -> 履约 -> 售后
- 运营配置 -> 门店生效 -> 数据回流 -> 报表/告警
- 审批 -> 治理 -> 导出/开放接口 -> 审计闭环
- 写操作 -> 审计事件 -> 追踪查询 -> 回放/举证

输出：

- 《关键流程穿透审计表》
- 《权限缺陷与越权风险清单》
- 《异常场景与恢复预案》
- 《审计底座差距清单》

### 第 5 轮：实施准备轮

目标：把所有差异项转化为可开发、可测试、可上线的任务规划。

输出：

- 《模块优先级清单》
- 《里程碑计划》
- 《资源配置表》
- 《质量关口与风险预案》
- 《RACI 责任矩阵》
- 《上线阻断清单》

## 6. 当前初步发现的重点风险

1. 三端资料很多，但尚缺一份“PRD -> 页面/接口 -> 测试 -> 验收”的总映射表。
2. 管理后台存在大量角色工作台与页面门禁，但“角色名称、前端门禁串、后端 RBAC 正式角色名”并未完全统一。
3. 部分页面仍可能处于 mock 或半联调状态，容易造成“看起来有功能，实际上链路未闭环”的假完成判断。
4. API 侧虽然已逐步完成多轮权限收口，但全仓仍需持续审计剩余真实 controller，不能轻易下“全部完成”结论。
5. TOB 官网、TOC 官网和后台系统之间，仍需要系统化梳理“官网展示、用户转化、后台配置、治理能力”的跨端一致性。
6. 审计底座能力尚未形成独立专项交付线，容易被一般功能排期稀释。
7. 如果不把 App、Pad、Miniapp、OpenAPI 明确纳入边界，最终结论会天然失真。

### 7.3 资源配置

资源配置不再只写人数，采用 `RACI + 投入比例 + 并行上限`。

#### RACI 核心原则

- `A`：每个里程碑只能有 1 个最终 accountable owner
- `R`：必须包含业务、前端、后端、测试中的实际执行人
- `C`：包含安全、合规、数据、SRE 等咨询角色
- `I`：管理层、相关产品线和相邻专项负责人

#### 关键职责分配

1. 战略与产品组
   - A：M0
   - C：M1 ~ M5
2. 架构与平台组
   - A：M3
   - C：M0、M1、M4、M5
3. TOB 官网组
   - R：TOB 官网链路审计
4. TOC 官网组
   - R：TOC 主链路与转化链路审计
5. 管理后台组
   - R：角色工作台与配置治理审计
6. 权限与合规组
   - A：M1
   - R：角色与权限统一
7. 交易与履约组
   - A：M2
   - R：交易、支付、履约、售后链路
8. AI 与开放平台组
   - R：开放平台、网关、Webhook、AI 审计
9. 质量与交付组
   - A：M5
   - C：所有阶段

#### 投入比例建议

- 产品与业务：15%
- 架构与平台：15%
- TOB / TOC / 后台分线：35%
- 权限合规与审计专项：15%
- 测试、交付、SRE：20%

#### 并行上限

- 同一时间最多并行 3 个高优专项
- 任一 owner 同时 accountable 的里程碑不得超过 1 个
- 涉及权限、审计底座的改动必须串行复核，不允许无门禁并行推进

### 7.4 迭代节奏

- 每轮审计建议 3~5 个工作日
- 每轮结束必须产出明确清单与阻断项
- 每个阶段结束必须有一次管理层复核与路线图校准
- 每个阶段统一复用现有 `Kickoff / Mid / Retro` 机制，不再另起评审制度

## 8. 质量关口

每个模块在进入实施前必须满足：

1. 有 PRD/需求卡映射
2. 有角色与工作台归属
3. 有前后端权限定义
4. 有页面/API/测试证据
5. 有上线阻断项与回滚思路

### 8.1 审计专项门禁

以下 7 条为强制 hard gate：

1. 所有高危写操作必须有审计事件定义
2. 核心链路必须完成 `trace_id` 贯通
3. 权限收口改动必须具备 `metadata test + diagnostics = 0 + 定向回归通过`
4. 审计写入与业务写入的一致性必须有校验方案
5. 哈希链 / 防篡改能力必须有验证机制
6. 快照、归档、查询、回放至少完成抽样验证
7. mock / fallback / 假 API 页面不得计入闭环完成率

### 8.2 证据可信度分级

证据按可信度划分为：

- `A 级`：源码、测试、运行日志、诊断、回归结果
- `B 级`：设计文档、PRD、需求卡、评审纪要
- `C 级`：口头结论、人工说明、未附源码的截图

项目级复签只接受 `A + B` 组合，不接受仅凭 `C 级` 证据结论。

## 9. 风险预案

风险预案统一采用“五元组”结构：`触发条件 / 监控指标 / 责任人 / 处置时限 / 回退动作`。

### 9.1 风险矩阵

1. 文档版本冲突
   - 触发条件：PRD、roadmap、需求卡三者描述冲突
   - 监控指标：冲突项数量、未签收变更数
   - 责任人：产品负责人
   - 处置时限：24 小时内裁决
   - 回退动作：冻结需求变更，回退到最近已签字版本
2. 角色命名不统一
   - 触发条件：业务角色、页面工作台、RBAC 正式角色不一致
   - 监控指标：未映射角色数
   - 责任人：权限负责人
   - 处置时限：48 小时内收敛
   - 回退动作：暂停角色工作台审计，先修主数据
3. mock / fallback 误判
   - 触发条件：页面依赖 mock 数据或 fallback bootstrap
   - 监控指标：mock 页面数、未联调页数
   - 责任人：前端负责人
   - 处置时限：每轮结束前清点
   - 回退动作：从完成清单移出，转入缺口清单
4. 权限收口遗漏
   - 触发条件：高危 controller 存在裸露写接口
   - 监控指标：未挂 `RequireTenantScope` 或权限元数据的接口数
   - 责任人：后端负责人
   - 处置时限：72 小时内修补并回归
   - 回退动作：阻断上线，不接受人工豁免
5. 审计底座缺失
   - 触发条件：关键写操作没有审计事件、trace_id 不贯通、无法查询举证
   - 监控指标：审计覆盖率、trace_id 贯通率、回放通过率
   - 责任人：E54 审计专项负责人
   - 处置时限：进入上线门禁前必须关闭
   - 回退动作：对应能力降级为不可上线
6. 跨端链路断裂
   - 触发条件：官网展示、后台配置、API、生效数据链未闭环
   - 监控指标：断点链路数、抽样失败率
   - 责任人：平台负责人
   - 处置时限：每阶段结束前复核
   - 回退动作：回退到单端能力验收，不得宣称全链完成
