## 2. 规划输入

### 2.1 已冻结输入

1. 角色主数据字典已冻结，角色命名以 `PLATFORM_ADMIN / TENANT_ADMIN / STORE_MANAGER / CASHIER / SALES_GUIDE` 等正式口径为准。
2. 系统边界矩阵已冻结，全局主统计范围只覆盖：
   - `apps/api`
   - `apps/admin-web`
   - `apps/storefront-web`
   - `apps/tob-web`
3. E54 审计底座已独立成专项，不允许与普通业务排期混算。
4. 证据字段标准已冻结，所有规划输出后续必须能落到 `evidence_id / source / proof / confidence`。

### 2.2 当前主链现状

根据已完成的多轮审计，当前优先级按业务损失和复签风险冻结为：

| 优先级 | 主链 / 主题 | 当前结论 | 主要风险 |
| --- | --- | --- | --- |
| `P0` | 预约主链 | TOC 执行面最强，Admin 控制面仍不可信 | 配置 -> 生效 -> 履约反馈证据不足 |
| `P0` | 收银支付主链 | TOC + API 真链较强，Admin 财务面存在 mock / fallback | 财务控制面不可完整复签 |
| `P0` | 会员主链 | TOC 主链可用，Admin / TOB 偏运营面 | `member` / `membership` 双口径 |
| `P0` | 治理配置主链 | API 能力与 TOB 联动存在，Admin 主控制面可信度不足 | mock / fallback 治理页误判 |
| `P1` | 营销回流主链 | 多点存在，缺穿透表 | 配置 -> 承接 -> 回流断裂 |
| `P1` | 报表财务口径链 | 页面与接口均存在 | 指标口径未完全冻结 |
| `P1` | 工作台治理链 | TOB / Admin 双治理面共存 | 职责边界未彻底写清 |

## 3. 规划原则

1. 源码证据先行，不以页面数量代替完成率。
2. 对齐已有功能，不新造业务口径和角色口径。
3. 先收 `P0` 主链与控制面可信度，再做增强域。
4. 所有里程碑必须包含 `Owner / 输入 / 输出 / DoD / 阻断项 / 签字人`。
5. 所有阶段都必须具备代码、配置、证据、回滚四要素。
6. `mock / fallback` 页面必须显式标注，且不得计入闭环完成率。

## 4. 阶段规划

### 4.1 阶段总览

| 阶段 | 名称 | 目标 | 建议周期 | 进入条件 | 退出条件 |
| --- | --- | --- | --- | --- | --- |
| `S0` | 基线锁定 | 冻结角色、边界、证据、底座约束 | 1 周 | 专家总控方案完成复审 | 前置工件全部冻结 |
| `S1` | 角色与控制面可信化 | 收口高危角色、权限、控制面来源态 | 2 周 | `S0` 完成 | 角色-权限-流程一致性可复核 |
| `S2` | P0 主链穿透收口 | 预约、支付、会员、治理四条主链形成真闭环底稿 | 3 周 | `S1` 完成 | 4 条 P0 主链均有穿透证据与阻断清单 |
| `S3` | 审计底座落地 | E54 审计专项进入接入、双写、校验阶段 | 3 周 | `S1` 完成，可与 `S2` 局部并行 | 高危写操作审计覆盖与 `trace_id` 贯通可验证 |
| `S4` | P1 域扩展与统一口径 | 营销、报表、工作台治理链转入标准化 | 2 周 | `S2` 主结论冻结 | 口径附录、跨端职责分层与回流表完成 |
| `S5` | 上线门禁与复签 | 风险归零或签署接受，进入统一复签 | 1 周 | `S3`、`S4` 满足最低验收 | P0 阻断清零，门禁全部签字 |

### 4.2 当前建议顺序

当前执行顺序建议采用：

1. `S1` 角色与控制面可信化
2. `S2` P0 主链穿透收口
3. `S3` 审计底座落地
4. `S4` P1 域扩展与统一口径
5. `S5` 上线门禁与复签

原因：

- 当前最影响复签的不是“有没有更多页面”，而是控制面是否可信。
- 预约、支付、会员、治理四条主链决定主系统是否能形成真实闭环。
- 审计底座必须跟主链接入并行推进，但不能挤占主链收口节奏。

## 5. 里程碑卡

### 5.1 M0 基线锁定

- Owner：项目经理
- Accountable Group：战略与产品组
- 输入：
  - `expert54-full-process-audit-plan.md`
  - `role-master-dictionary.md`
  - `system-boundary-matrix.md`
  - `evidence-field-standard.md`
- 输出：
  - 角色主数据冻结版
  - 系统边界冻结版
  - 审计证据字段标准
  - 来源态判定标准
- DoD：
  - 角色命名无冲突
  - 审计主边界无争议
  - `mock / fallback / api` 判定规则冻结
- 阻断项：
  - 角色主数据仍存在双名并行
  - App / Pad / Miniapp 统计口径未冻结
- 签字人：
  - 产品负责人
  - 架构负责人
  - 交付负责人

### 5.2 M1 角色与权限闭环

- Owner：权限与合规组负责人
- Accountable Group：权限与合规组
- 输入：
  - 角色主数据字典
  - 工作台能力矩阵
  - 页面门禁与后端权限证据
- 输出：
  - `角色-权限-流程一致性审计表`
  - 高危权限缺口清单
  - 控制面来源态标注结果
- DoD：
  - 高危角色工作台入口、门禁、API、测试证据可追溯
  - `Admin` 关键控制面来源态全部落标
  - 高危 controller 无裸露写接口
- 阻断项：
  - 页面门禁与 API 权限串不一致
  - mock 页仍被错误计入完成率
- 签字人：
  - 后端负责人
  - 前端负责人
  - 测试负责人

### 5.3 M2 P0 主链穿透收口

- Owner：交易与履约组负责人
- Accountable Group：交易与履约组
- 输入：
  - 三端对齐表
  - 跨端链路断点清单
  - 预约 / 支付 / 会员 / 治理穿透底稿
- 输出：
  - 4 条 P0 主链穿透审计结论
  - 主链阻断项清单
  - 真链、伪闭环、风险链分层表
- DoD：
  - 每条主链均有执行面、控制面、API 面三层证据
  - 每条主链均明确 `已通 / 部分通 / 断点`
  - 所有主链均有回退与补齐建议
- 阻断项：
  - 主链关键节点仍依赖 mock
  - API 口径未统一
- 签字人：
  - 业务负责人
  - 平台负责人
  - 运营负责人

### 5.4 M3 审计底座闭环

- Owner：E54 审计专项负责人
- Accountable Group：架构与平台组
- 输入：
  - `e54-audit-foundation-implementation-plan.md`
  - 高危写操作审计事件清单
  - `trace_id` 贯通规范
- 输出：
  - 审计事件模型冻结版
  - EventStore 双写迁移表
  - 哈希链与快照验证方案
- DoD：
  - 高危写操作审计覆盖形成可验证清单
  - `trace_id` 贯通到请求、审计记录、事件存储
  - 持久化与双写不再停留于纯内存结论
- 阻断项：
  - `Map` 审计日志未迁移
  - 快照、回放、举证方案缺失
- 签字人：
  - 审计负责人
  - 安全负责人
  - SRE 负责人

### 5.5 M4 P1 域统一与扩展

- Owner：TOB 官网组负责人
- Accountable Group：TOB 官网组 + 管理后台组
- 输入：
  - 营销、报表、治理链相关审计底稿
  - 财务与报表口径附录
- 输出：
  - 营销回流主链穿透表
  - 报表财务口径附录
  - TOB / Admin 治理职责分层表
- DoD：
  - `P1` 三个主题具备统一职责与口径
  - 页面值不再直接替代业务指标结论
- 阻断项：
  - 报表口径未冻结
  - TOB / Admin 双治理面仍职责重叠
- 签字人：
  - 数据负责人
  - 产品负责人
  - 平台负责人

### 5.6 M5 上线门禁与复签

- Owner：质量与交付组负责人
- Accountable Group：质量与交付组
- 输入：
  - 所有里程碑结论
  - 风险矩阵
  - 回滚与恢复预案
- 输出：
  - 上线阻断清单
  - 最终优先级路线图
  - 复签纪要
- DoD：
  - P0 阻断项全部关闭或签署接受
  - 关键链路具备回归、审计、回退三类证据
  - 复签结论附 `A + B` 级证据组合
- 阻断项：
  - 仍有高危未签字风险
  - 仍有缺证链路
- 签字人：
  - 管理层
  - 产品负责人
  - 架构负责人
  - 交付负责人

## 6. 资源配置

### 6.1 编组与投入比例

| 专家组 | 核心职责 | 计划投入比例 | 主要对口执行域 |
| --- | --- | --- | --- |
| 战略与产品组 | 基线、需求裁决、优先级 | `12%` | M0 / M5 |
| 架构与平台组 | 审计底座、跨端架构、技术门禁 | `16%` | M3 / M5 |
| TOB 官网组 | 企业门户、开放平台、联动展示面 | `10%` | M4 |
| TOC 官网组 | 预约、支付、会员执行面 | `12%` | M2 |
| 管理后台组 | 工作台、治理、财务、会员控制面 | `14%` | M1 / M2 / M4 |
| 权限与合规组 | RBAC、多租户、权限收口 | `14%` | M1 |
| 交易与履约组 | 订单、支付、预约、售后 | `10%` | M2 |
| AI 与开放平台组 | 网关、Webhook、开放平台、AI 扩展域 | `5%` | M4 |
| 质量与交付组 | 诊断、回归、门禁、发布 | `7%` | M5 |

### 6.2 工程侧映射

| 工程域 | 主要责任对象 | 协作对象 |
| --- | --- | --- |
| `apps/api` | 后端负责人 | 权限与合规组、架构与平台组 |
| `apps/admin-web` | 管理后台负责人 | 权限与合规组、质量与交付组 |
| `apps/storefront-web` | TOC 前端负责人 | 交易与履约组 |
| `apps/tob-web` | TOB 前端负责人 | TOB 官网组、AI 与开放平台组 |
| 审计底座专项 | 平台负责人 | 审计负责人、安全负责人、SRE |

### 6.3 并行上限

1. 同一时间最多并行 3 个高优专项。
2. `M1` 与 `M2` 可局部并行，但同一业务域不得同时做“权限收口”和“大规模流程改造”。
3. 审计底座接入涉及财务、权限、治理等高危域时，必须串行复核。
4. 任一 Accountable Owner 同时只允许承担 1 个里程碑。

## 7. 迭代节奏

### 7.1 标准节奏

| 节点 | 频率 | 目标 |
| --- | --- | --- |
| `Kickoff` | 每阶段开始前 | 冻结 scope、证据口径、验收口径 |
| `Mid Review` | 每周中段 | 校准阻断项、确认偏差、调整资源 |
| `Retro / Sign-off` | 每阶段结束时 | 输出审计结论、关闭或升级风险 |
| 管理层复核 | 每个里程碑结束后 | 决定是否进入下一里程碑 |

### 7.2 每周节奏建议

1. 周一：冻结本周 scope 与证据口径。
2. 周二到周四：源码审计、页面/API 对齐、缺口清单补齐。
3. 周五：做 diagnostics、定向回归、风险复盘与下一周排程。

## 8. 风险预案

### 8.1 风险矩阵

| riskId | 风险 | 触发条件 | 监控指标 | 责任人 | 处置时限 | 回退动作 |
| --- | --- | --- | --- | --- | --- | --- |
| `RISK-PLAN-0001` | 角色口径反复变更 | 新需求绕过角色主数据字典 | 未映射角色数 | 权限负责人 | 24h | 暂停角色审计，回退到已冻结角色口径 |
| `RISK-PLAN-0002` | 控制面伪闭环 | mock / fallback 页面被算作完成 | 未落标页面数、伪完成页面数 | 前端负责人 | 当周内 | 从完成清单移除，转入缺口清单 |
| `RISK-PLAN-0003` | API 权限回退 | 新增 controller 未复用既有权限串 | 裸露接口数、metadata 缺失数 | 后端负责人 | 48h | 阻断合并，补 metadata test 与回归 |
| `RISK-PLAN-0004` | 主链口径分裂 | 同一业务域存在双入口或双模型 | 双口径接口数 | 业务负责人 | 72h | 暂停迁移，先补 canonical model |
| `RISK-PLAN-0005` | 审计底座失真 | 写操作无审计事件或 `trace_id` 不贯通 | 审计覆盖率、trace 贯通率 | 审计专项负责人 | 进入 M5 前必须关闭 | 对应能力不得上线 |
| `RISK-PLAN-0006` | 跨端链路断裂 | 配置结果未回流到展示或控制面 | 断点链路数 | 平台负责人 | 每阶段复核 | 回退为单端验收，不得宣称全链完成 |
| `RISK-PLAN-0007` | 指标口径不统一 | 报表、财务、经营数字互相冲突 | 口径冲突项数 | 数据负责人 | 72h | 冻结经营复签，回退到已签字口径 |

### 8.2 风险分级处置

1. `P0` 风险：24 小时内拉齐责任人，阻断里程碑推进。
2. `P1` 风险：72 小时内给出修补方案和补证计划。
3. `P2` 风险：纳入下一阶段迭代，但不得影响当前 P0 / P1 门禁。

## 9. 质量关口

### 9.1 阶段通用门禁

所有阶段必须满足：

1. 有需求来源。
2. 有源码证据。
3. 有权限与角色归属。
4. 有 diagnostics 结果。
5. 有定向回归或等价验证。
6. 有回滚与降级说明。

### 9.2 上线前强制门禁

1. 高危 controller 权限元数据收口完成。
2. `Admin` 关键控制面来源态已全部落标。
3. `P0` 主链穿透结论完成并附带风险说明。
4. 审计专项至少完成最低验收。
5. 仍为 `mock / fallback` 的页面不得进入闭环完成率。

## 11. 冻结结论

1. 当前项目的下一阶段不再是继续横向铺页面，而是围绕 `P0 主链可信度 + 控制面可信度 + 审计底座可信度` 三条线并行推进。
2. 资源配置必须向 `Admin 控制面可信化`、`P0 主链穿透`、`E54 审计底座` 三个方向倾斜。
3. 在 `mock / fallback`、双口径、裸露权限、审计底座未落地之前，不得出具“已全部搞定”类结论。
